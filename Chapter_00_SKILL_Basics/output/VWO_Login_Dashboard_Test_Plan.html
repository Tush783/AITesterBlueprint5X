Objective

Verify that the VWO login experience provides secure, reliable, accessible, and responsive access to the VWO platform. Testing will check the login and recovery journeys, user input handling, enterprise authentication features, security controls, performance expectations, and usability requirements described in the PRD.

Scope

In Scope

  1. Authentication
    • Email and password login, including successful and unsuccessful attempts.
    • Remember Me behavior and session handling, including configured timeout behavior where the configuration is available.
    • Optional multi-factor authentication (2FA).
    • Enterprise single sign-on (SSO), including the protocols listed in the PRD (SAML and OAuth).
    • Successful transition to the VWO platform and preservation of recent activity where supported.
  2. Input validation and error handling
    • Email format validation and validation feedback on blur.
    • Password validation and any displayed password requirements or strength feedback.
    • Missing, malformed, and boundary input values.
    • Clear and actionable authentication and recovery errors without exposing sensitive information.
  3. Password recovery and account access
    • Forgot-password initiation and email-based reset.
    • Secure reset-token behavior and password-complexity enforcement.
    • Recovery and support paths described by the implemented product.
  4. Login-page experience
    • VWO branding, announcement banner, registration/free-trial link, and available Light and Dark themes.
    • Initial focus, clickable labels, loading feedback, and responsive layout.
    • Keyboard navigation, screen-reader support, high-contrast accessibility, and WCAG 2.1 AA checks.
  5. Security and privacy
    • HTTPS enforcement and secure transmission of authentication data.
    • Session-token handling, session security, and configured session timeouts.
    • Rate limiting and resistance to repeated unauthorized login attempts.
    • Password storage and handling against the security requirements in the PRD.
    • GDPR/CCPA-related handling of user data and enterprise audit requirements, where applicable to the login flow.
  6. Performance, availability, and integrations
    • Login page load time against the stated target of under 2 seconds on standard connections.
    • Login response and stability under normal, peak, and concurrent access conditions.
    • The stated target of thousands of simultaneous login attempts, once a specific load profile is agreed.
    • Authentication success/failure analytics and customer-support integration.
    • Availability and geographic performance requirements where the relevant environment and monitoring are available.
  7. Regression and exploratory testing
    • Regression after fixes or changes to login, recovery, session, theme, or integration behavior.
    • Exploratory testing of key user journeys and error recovery.

Out of Scope

  • Biometric authentication, adaptive/risk-based authentication, and Progressive Web App functionality are listed as future enhancements and are excluded unless separately approved.
  • Testing functionality outside the login, account recovery, and directly connected access flows is excluded, except for verifying the transition into the VWO platform.
  • Production load or security testing is not assumed; environment authorization and scope must be confirmed before such testing.

Inclusions

The test suite will cover these user flows and conditions:

  • Returning user login with valid credentials.
  • Invalid credentials, invalid email format, empty fields, and validation on blur.
  • Remember Me selected and not selected, including resulting session behavior.
  • Login loading state, repeated submission behavior, and clear success/failure feedback.
  • Forgot-password initiation, email-based recovery, token validity, and password requirements.
  • 2FA and SSO login paths when enabled in the test environment.
  • Free-trial registration link and product announcement/theme options.
  • Successful redirection to the VWO dashboard and session/context behavior.
  • Keyboard-only and screen-reader access to all login-page controls.
  • Mobile and desktop responsive layouts and touch-friendly controls.
  • HTTPS, session, throttling, audit, privacy, and authentication-analytics checks.
  • Performance under agreed traffic profiles and login page load-time measurement.

Test Strategy

Testing will be performed in phases:

  1. Requirement analysis and test design
    • Derive scenarios from the PRD and confirm unresolved requirements, environment details, and acceptance thresholds.
    • Use equivalence partitioning, boundary-value analysis, decision tables, state-transition testing, use-case testing, error guessing, and exploratory testing.
    • Prioritize core login, recovery, session security, and accessibility paths.
  2. Smoke and sanity testing
    • Verify that the login page loads and that the primary login and recovery entry points are available.
    • Reject the build for in-depth testing if critical smoke checks fail; resume after a stable build is provided.
  3. Functional and integration testing
    • Execute approved test cases across login, recovery, session, 2FA/SSO, analytics, support, and dashboard transition flows.
    • Verify both positive and negative outcomes, validation, error feedback, and state changes.
  4. Non-functional testing
    • Check responsive behavior, accessibility, security controls, and the PRD's performance targets.
    • Conduct concurrency/load validation only with an agreed workload profile and an authorized non-production environment.
  5. Regression, retesting, and exploratory testing
    • Retest resolved defects and run targeted regression after changes.
    • Repeat test cycles until exit criteria are met or remaining risks are accepted.

Testing should begin as early as requirements and builds are available (shift-left), with multiple testers using supported environments in parallel where resources permit.

Entry and Exit Criteria

Requirement Analysis

Entry criteria

  • The PRD or equivalent approved requirements are available to the test team.

Exit criteria

  • Requirements and supported login paths have been reviewed.
  • Open questions and assumptions affecting testability have been recorded and assigned for clarification.

Test Design

Entry criteria

  • Requirement analysis has started and the login flows in scope are identified.

Exit criteria

  • Test scenarios and cases cover the agreed scope and are reviewed/approved by the designated stakeholders.
  • Test data, environment, and required access needs are documented.

Test Execution

Entry criteria

  • Test scenarios and cases are approved.
  • The application build and test environment are available.
  • Required test accounts, credentials, email recovery access, and SSO/2FA configuration are ready for applicable cases.
  • Smoke tests pass.

Exit criteria

  • Planned test cases have execution results; blocked and unexecuted cases are identified with reasons.
  • Critical and high-priority failures are reported and triaged.
  • Fixed defects in the agreed release scope are retested, with regression completed as agreed.
  • Remaining defects and risks are documented for release decision-making.

Test Closure

Entry criteria

  • Test execution and required retesting are complete or formally stopped.
  • Test and defect reports are available.

Exit criteria

  • Test summary, coverage, open risks, and outstanding defects are communicated.
  • Required stakeholder approval or acceptance of residual risk is recorded.

Test Execution

  • Run smoke checks on each build before detailed testing.
  • Record results as pass, fail, blocked, or not run, with build/environment details and evidence.
  • Log defects with concise reproduction steps, expected and actual results, severity/priority, and screenshots or logs where appropriate.
  • Retest fixes and run regression tests on affected flows.
  • Communicate execution progress and significant blockers to stakeholders; reporting cadence and channels are TBD.

Defect Reporting Procedure

  1. Confirm that the observed behavior deviates from the approved requirement or expected user experience.
  2. Record a reproducible defect with environment/build, preconditions, steps, expected result, actual result, and relevant evidence.
  3. Triage severity and priority with the responsible product and engineering stakeholders.
  4. Track status through resolution, retest, and closure in the project-approved defect tracking tool (TBD).
  5. Communicate critical blockers and test-cycle status through the agreed stakeholder channel (TBD).

Defect tracking tool, severity definitions, ownership assignments, and communication cadence are not specified in the PRD and must be confirmed.
